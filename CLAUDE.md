## Architecture

**Two-stage AI pipeline**, both going through `src/lib/generateSteps.ts` / their own routes:
1. `POST /api/vision-analyze` (`src/app/api/vision-analyze/route.ts`) — sends the board's actual pinned images (client-resized to a 768px max edge, JPEG data URLs — see `src/lib/image.ts`) to GPT-4o vision, grouped by category, asking for one `description` (what it actually sees) + one specific clarifying `question` per life area present. This is what powers the per-category question shown before the final checklist.
2. `POST /api/analyze` (`src/lib/generateSteps.ts`'s `generateSteps()`) — takes the category, image count, the vision description, the user's typed answer, and server-computed calendar context (`getCalendarContext()` in `src/lib/yearProgress.ts`: today's date, days/weeks/months left). Returns `{ goal, steps }`: a short (5-8 word) named objective plus 3-4 short imperative checklist items scaled to the remaining year — most ambitious still-doable step, never "finish the whole goal" when the calendar makes that impossible (PRODUCT.md principle 5). Model is also prompted hard against writing meta/vague items (see PROJECT_STATE.md — this exact failure mode shipped once and was fixed).
3. `POST /api/refine-step` — same `generateSteps()` call scoped to one category, given the original answer plus a follow-up note and the same server-computed calendar context, so a user can iteratively narrow one area without re-running vision analysis or the other categories.

**Category system**: 5 fixed categories (`career`/`health`/`relationships`/`travel`/`finance`), `src/lib/categories.ts`. Each has a solid color (used only in the segmented filter's active state) and a tonal pastel tint + saturated text color (used everywhere else — badges, chips). `CATEGORY_META`'s `ink` is white for 4 of the 5 and near-black for `travel` specifically (its gold is too light for white text at 4.5:1 — verified by computed contrast, don't revert without rechecking).

**Board canvas** (`src/components/BoardCanvas.tsx`, `ImageCard.tsx`): freeform-but-tidy placement — new images auto-flow into a loose grid with slight rotation jitter on add, then are freely draggable (pointer events, snapped to an 8px grid on release). No canvas library; it's plain absolutely-positioned divs.

**Client-only state**: `images`, `answers`, `insights`, `results`, `checkedSteps` all live in `src/app/page.tsx`'s `useState`. Nothing persists past a reload. This is a known, intentional gap — see PROJECT_STATE.md.

## Conventions

- **Design tokens**: `src/app/globals.css` (CSS custom properties) mapped into Tailwind via `@theme inline`. `DESIGN.md` is the source of truth for the visual system — read it before styling anything, and update it if you change the committed world (see its own "Do's and Don'ts").
- **Icons**: hand-authored single-stroke SVGs only, in `src/components/icons.tsx` (`strokeWidth={1.75}`, round caps). Never a unicode glyph or emoji standing in for an icon — this is an explicit DESIGN.md rule that was violated once and fixed.
- **Type floor**: nothing renders below `text-xs` (12px) anywhere in this app — a literal smaller value (`text-[10px]`/`text-[11px]`) has been introduced and caught by the design-quality hook more than once; use `text-xs` even when a component feels cramped.
- **Contrast**: any new color pairing (button fill + text, tint + text) needs a computed check (`(L1+0.05)/(L2+0.05)`, WCAG relative luminance) against 4.5:1 before shipping — this isn't optional polish, real failures have shipped and been caught this way twice (the original brand coral and the original health-category green both failed at first pass).
- **Contained hit boxes for overflowing decorative elements**: an absolutely-positioned icon/badge that visually overflows its own clickable parent (e.g. `ImageCard`'s tap-hint icon poking outside the category pill) is NOT clickable in that overflow region unless the parent's own box is grown via padding to actually contain it — `pointer-events-none` + raw overflow looks right but silently breaks click-ability at the edges. See `ImageCard.tsx`'s inline comment for the exact padding/anchor-offset math (which edge of padding you add depends on which edges the element is anchored from — bottom/right padding needs a compensated anchor offset, top/left doesn't, or vice versa; work it out fresh with the CSS box model rather than guessing, it's counter-intuitive).
- **Client components deriving from "now"** (a clock, a random value): initialize state to a null/placeholder value (not a lazy `useState` initializer that calls `Date.now()`/`Math.random()` directly), and compute the real value only inside `useEffect`. Even then, don't call `setState` synchronously as the first line of the effect body — wrap it in `setTimeout(fn, 0)` — or the `react-hooks/set-state-in-effect` lint rule fails the build. See `YearCountdown.tsx`, `WeeksGrid.tsx`, and `page.tsx`'s tap-hint-dismissed check for the working pattern.
- **Never fake a feature that isn't wired.** A nav item or control for something not actually built (accounts, in this app's case) gets rendered visually muted/disabled (`opacity-60`, `cursor-not-allowed`), never as if it works. This was a real shipped mistake (a fake signed-in avatar) that got corrected.

## Known gotchas

- **Google Fonts don't load via `next/font/google` in this dev sandbox** — the Next dev server process can't reach `fonts.googleapis.com` even though the Bash tool's `curl` can. Self-host instead: `curl` the actual `.woff2` file (fetch the Google Fonts CSS with a Chrome UA to get the real `fonts.gstatic.com` URL, then download that) into `src/fonts/`, and load it with `next/font/local`. A discrete-weight request (e.g. `wght@400;500;600`) to Google Fonts may resolve to a single variable-font file covering the whole range — check before downloading one file per weight.
- **Turbopack dev can serve stale output after a font/config swap** — if a fixed hydration/font issue still shows in the browser after editing, `rm -rf .next` and restart the dev server before concluding the fix didn't work.
- Screenshot tooling in the Browser pane can under-report true viewport height (renders a scaled-down capture) — when content seems to be cut off or a button seems unreachable, resize the window taller and/or drive the click via a JS `querySelector` + `.click()` instead of trusting on-screen pixel coordinates.
